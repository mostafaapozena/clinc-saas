# المرحلة 6 — التجربة والقبول
## الموجود
اختبارات آلية وبيانات تجريبية، لا دليل في التقرير على تجربة عيادة فعلية واعتماد سريري/محاسبي/قانوني.
## الهدف
إثبات سهولة الاستخدام وصحة التشغيل مع نطاق محدود، قبل تسويق وعود عامة أو فتح آلاف الاشتراكات.

## 6A — قبول المالك على staging
يمكن تنفيذ جولات مبكرة بعد 5A، حتى قبل إغلاق كل وظائف المنتج. النتيجة ملاحظات مرحلية وليست إغلاق 6.
بحساب جديد لا demo جاهز: الموقع → solution → signup → إعداد المنشأة → تجهيز workspace → dashboard مناسبة → تجهيز الأقسام → مريض → موعد → وصول → طبيب → سجل → فاتورة → تحصيل → تقرير.
كرر للأسنان وENT والعلاج الطبيعي ومركز متعدد مع AR/EN والجوال واللابتوب، ولوحة المشغّل منفصلة.
حدد نقاط التعثر والوقت لإنجاز أول مهمة والأخطاء والمساعدة المطلوبة. لا يتطلب التذوق البصري بيانات مرضى حقيقية.

## 6B — pilot محدود
الدخول: قبول وظائف النطاق، staging مقبول، وبوابات التشغيل الآمنة للبيئة الفعلية مستوفاة. أي استخدام لبيانات مرضى يحتاج مراجعات وسياسات واعتمادات وإقامة بيانات وضوابط كاملة تخص ذلك الاستخدام.
حدد عيادة/فرعًا وأدوارًا وتخصصًا ومدة وخطة دعم وقائمة وظائف. ابدأ بتخصص واحد مناسب؛ لا تفترض اعتماد كل تخصص من نجاح عيادة واحدة.
خطة ترحيل وتجربة واسترجاع بيانات وتدريب، قناة incident وتصعيد ومسؤول مناوب، آلية توقف آمن عند مشكلة مؤثرة.

## القبول والقياس
- الرحلات المحددة تعمل دون تدخل المطور الروتيني.
- البيانات والمؤشرات مطابقة لمصادرها مع محاسب/طبيب حسب المجال.
- لا وصول غير مأذون أو فقد/تكرار بيانات.
- SLOs متفق عليها ونتائج مراقبة واستعادة موثقة.
- سهولة البدء ووقت أول قيمة والتذاكر والاحتفاظ تُقاس بعينة معروفة، لا نسب تسويق مخترعة.
- ملاحظات UX تصنف: تمنع العمل / تربك / تحسين اختياري، مع owner وموعد مراجعة.
- قبول مكتوب من صاحب المنتج والمستخدمين المعنيين، ولا عيوب مؤثرة غير معالجة ضمن النطاق.

## مسارا البيع
SaaS موحد: باقات وحدود وتجربة وسياسة دعم وإلغاء وتصدير بيانات واضحة ومطبقة فعليًا.
المشروع المخصص: طلب وعرض ونطاق وتسعير وتسليم منفصل؛ لا fork عشوائي يكسر تحديثات SaaS، ولا تتحول كل رغبة عميل إلى ميزة عامة.
الدخل متكرر لكنه يحتاج دعمًا وتشغيلًا وتحصيلًا؛ لا تقدمه كدخل بلا تكلفة.
## الإغلاق والتوسع
تقرير pilot ومشاكله وقراراته وإصدار مقبول وخطة إطلاق تدريجي. فتح الجمهور أو الإنتاج لا يتم تلقائيًا بمجرد نجاح suite.
ما بعد ذلك backlog مستقل؛ لا وصف «100% لكل المجالات». النطاق المعتمد هو المرجع.
## قواعد ملزمة عند التنفيذ
- هذا ملف تخطيط معتمد على تقرير المرحلة صفر الذي أرسله المالك، وليس فحصًا مستقلًا للكود. خط الأساس المبلّغ: main عند 74ad659؛ وثائق المرحلة صفر في PR #39، commit 621de78. تحقق من الحالة الحالية قبل العمل ولا تعد تنفيذ المكتمل.
- اقرأ تعليمات المشروع وdocs/delivery-plan/ أولًا. هذه الملفات تنظم التنفيذ ولا تمحو الأدلة التاريخية. سجل أي تعارض مع السبب والدليل.
- حافظ على الهوية المعتمدة: raclinic منتج Devware، العربية RTL وAlexandria، الإنجليزية LTR وInter، فاتح/داكن/حسب الجهاز.
- نفّذ مرحلة واحدة فقط. الأفكار الجديدة في قائمة انتظار؛ لا توسّع النطاق تلقائيًا. الأعمال المستقلة داخل المرحلة يمكن توزيعها بين الفريق.
- الأدوار المقترحة وظائف عمل وليست افتراضًا لوجود موظفين إضافيين. عيّن مسؤولًا ومراجعًا لكل مهمة عند بدء المرحلة.
- لا تغيّر صلاحيات سريرية أو سياسة مالية أو تسعيرًا كأثر جانبي لتحسين الواجهة. API هو مرجع التفويض؛ إخفاء الرابط لا يكفي.
- التطوير والتحقق في Codespace؛ لاحقًا النشر إلى staging عبر إصدارات محددة، وليس تعديل كود مباشر على الخادم.
- بيانات تجريبية فقط حتى اجتياز شروط التشغيل الحقيقي. لا أسرار في Git أو التقارير أو لقطات الشاشة.
- اعمل باستقلالية في القرارات الروتينية المصرح بها، مع احترام صلاحيات الأدوات وحماية الفروع. لا force push أو تجاوز CI.
- احفظ التقدم في سجل التنفيذ. الحالة: لم تبدأ / قيد التنفيذ / قيد المراجعة / مكتملة ومتحقق منها / متوقفة بسبب محدد.
- لا تدّع تحققًا لم تنفذه. افصل نتيجة اليوم عن الدليل التاريخي، والمحاكاة عن التكامل الحقيقي.
- الإغلاق: كود ومراجعة واختبارات مناسبة وفحص واجهة وتوثيق وأدلة على نفس commit. لا تبدأ المرحلة التالية تلقائيًا.
