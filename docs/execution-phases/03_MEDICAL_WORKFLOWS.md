# المرحلة 3 — اكتمال المسار الطبي
## الموجود
المرضى والحجز والوصول والسجل واعتماد/ملحق وتغطية ونماذج تخصصية موجودة بحسب التقرير. لا مراجعة طبيب ممارس. ملف المريض بلا خط زمني موحد، أنواع الموعد نوعان ثابتان، وتوجد فجوات تقارير ودمج ملفات.
## الهدف
ملف مريض واضح ورحلات متصلة وآمنة، مع فصل التحقق البرمجي عن الاعتماد السريري.
## مهام
- MED-01: جلسات مراجعة مع طبيب لكل تخصص؛ توثيق الأقسام والحقول والرحلات والملاحظات واعتماد النسخة المحددة.
- MED-02: خط زمني يجمع المسموح فقط: الزيارات والتشخيصات والتقارير والحجوزات وروابطها. حالات توثيق فقط لغير المخول، لا تسرب من summary أو search أو counts.
- MED-03: أنواع موعد قابلة للتهيئة، مدة وتخصص/خدمة عند اللزوم؛ توافق البيانات القديمة وسلامة الحجز والتزامن.
- MED-04: دمج المرضى المكررين بصلاحية واضحة ومعاينة وتدقيق وحفظ المراجع، دون حذف سجلات معتمدة أو دمج تلقائي بالاسم. حسم هوية المريض والنطاق قبل التنفيذ.
- MED-05: تقارير تشغيل وتخصصات ذات تعريفات معتمدة، مع تجنب اشتقاق أحكام سريرية من بيانات ناقصة.
- MED-06: تحويل نتائج مراجعة الأطباء إلى مهام محددة؛ ضبط نسخ القوالب دون إعادة تفسير سجلات قديمة.
- MED-07: استكمال browser journeys للرحلات التي اختبرت على الخادم فقط؛ استخدم معرفات الجرد ولا تفترض ماهية الثمانية.
## الاعتماديات
المرحلة 2 للأنماط والتنقل؛ طبيب يراجع التغييرات السريرية؛ سياسة تغطية الطبيب الغائب وclinical lead تبقى على القرار المعتمد ولا تُفعّل عرضيًا.
## خارج النطاق
الوصفات والتحاليل والتأمين وبوابة المريض والمرفقات ليست إضافات تلقائية. سجلها كتوسعات مستقلة؛ إن اعتُمدت قبل البدء ثبّت متطلبات ومخاطر ومعايير منفصلة.
## الإغلاق
رحلات من التسجيل إلى التوثيق والمتابعة والفوترة؛ منع IDOR والتسرب عبر الفروع والمنشآت وسحب العضوية وتعارض التعديل. سجلات معتمدة غير قابلة للمحو، ملحقات واضحة، مراجعة ممارس موثقة أو حالة «بانتظار الاعتماد السريري» تمنع وصف الجاهزية السريرية.
verify وCI ودليل بشري للسيناريوهات المعتمدة، مع عدم اعتبار اختبارات UI شهادة طبية.
## قواعد ملزمة عند التنفيذ
- هذا ملف تخطيط معتمد على تقرير المرحلة صفر الذي أرسله المالك، وليس فحصًا مستقلًا للكود. خط الأساس المبلّغ: main عند 74ad659؛ وثائق المرحلة صفر في PR #39، commit 621de78. تحقق من الحالة الحالية قبل العمل ولا تعد تنفيذ المكتمل.
- اقرأ تعليمات المشروع وdocs/delivery-plan/ أولًا. هذه الملفات تنظم التنفيذ ولا تمحو الأدلة التاريخية. سجل أي تعارض مع السبب والدليل.
- حافظ على الهوية المعتمدة: raclinic منتج Devware، العربية RTL وAlexandria، الإنجليزية LTR وInter، فاتح/داكن/حسب الجهاز.
- نفّذ مرحلة واحدة فقط. الأفكار الجديدة في قائمة انتظار؛ لا توسّع النطاق تلقائيًا. الأعمال المستقلة داخل المرحلة يمكن توزيعها بين الفريق.
- الأدوار المقترحة وظائف عمل وليست افتراضًا لوجود موظفين إضافيين. عيّن مسؤولًا ومراجعًا لكل مهمة عند بدء المرحلة.
- لا تغيّر صلاحيات سريرية أو سياسة مالية أو تسعيرًا كأثر جانبي لتحسين الواجهة. API هو مرجع التفويض؛ إخفاء الرابط لا يكفي.
- التطوير والتحقق في Codespace؛ لاحقًا النشر إلى staging عبر إصدارات محددة، وليس تعديل كود مباشر على الخادم.
- بيانات تجريبية فقط حتى اجتياز شروط التشغيل الحقيقي. لا أسرار في Git أو التقارير أو لقطات الشاشة.
- اعمل باستقلالية في القرارات الروتينية المصرح بها، مع احترام صلاحيات الأدوات وحماية الفروع. لا force push أو تجاوز CI.
- احفظ التقدم في سجل التنفيذ. الحالة: لم تبدأ / قيد التنفيذ / قيد المراجعة / مكتملة ومتحقق منها / متوقفة بسبب محدد.
- لا تدّع تحققًا لم تنفذه. افصل نتيجة اليوم عن الدليل التاريخي، والمحاكاة عن التكامل الحقيقي.
- الإغلاق: كود ومراجعة واختبارات مناسبة وفحص واجهة وتوثيق وأدلة على نفس commit. لا تبدأ المرحلة التالية تلقائيًا.
