# المرحلة 2 — التخصصات ومعالجات التجهيز
## الموجود بحسب التقرير
التخصيص جزئي: نماذج سجل وقوائم عمل واختصارات وعناوين خاصة. القائمة الجانبية مشتركة، ولا مؤشرات أو تقارير أو إعداد تخصصي مكتمل. معالج المنشأة محفوظ ومستأنف وآمن من التكرار؛ قائمة ابدأ هنا 5 بنود. تغطية الإعداد 4/10 بحسب منهجية الجرد.

## الهدف والدخول
بعد إغلاق 1، اجعل التخصص المختار ينعكس على بيئة العمل الفعلية، مع أساس ERP واحد. موافقة طبيب مطلوبة للمحتوى السريري الجديد؛ لا تمنع ذلك بناء الإطار العام والتنقل والإعدادات غير السريرية.

## المهام
| ID | التنفيذ | القبول |
|---|---|---|
| SOL-01 | إعداد typed للتخصصات متكامل مع سجل الوحدات | مصدر واحد للتنقل والتفعيل دون اعتبار config بديلًا لتفويض API |
| SOL-02 | dashboards حسب الدور والتخصص | أسنان وENT وعلاج طبيعي تختلف بمهام حقيقية وبيانات مأذونة |
| SOL-03 | مركز /setup | الحالات محسوبة من البيانات الفعلية والصلاحيات |
| SOL-04 | إطار wizard مشترك | حفظ واستئناف ومراجعة وتخطي اختياري وإعادة محاولة وتزامن |
| SOL-05 | رحلات تجهيز الأقسام | عيادة وفريق وساعات وخدمات ومالية وخزائن ومخزون ومشتريات؛ ما لم يُبن بعد يظهر غير متاح، لا wizard زائف |
| SOL-06 | تخصصات متعددة وفروع | سياق واضح ومريض واحد وERP مشترك |
| SOL-07 | رحلة اختيار solution إلى dashboard | المقصود محفوظ عبر signup/login/reload دون إنشاء مكرر |
| SOL-08 | مصفوفة قبول | جديد/قديم/دور مقيد/تبديل منشأة/فرع/تخصص |

## تفاصيل التجربة
الأسنان: مخطط الأسنان والتاريخ وخطط العلاج. العلاج الطبيعي: التقييم والجلسات المرتبطة والخروج مع نفس scheduler. ENT: السجل والفحوص والمتابعة ضمن المنفذ والمراجع.
إظهار الأجزاء المشتركة حسب صلاحيات المستخدم، وليس منع الحسابات من المحاسب أو كشف سجلات سريرية للمالك بسبب تخصص المنشأة.
«جار تجهيز بيئة العمل» يعكس عمليات حقيقية بلا تأخير مصطنع أو نسبة وهمية. لا تكرر إنشاء المنظمة أو الأرصدة عند الضغط/التبويبات.
الموديول الاختياري لا يمنع حجز أول موعد. HR غير المبني يؤجل wizard الخاص به للمرحلة 4، ويسجل كتبعيات. اختلاف dashboard ليس مجرد تغيير اسم أو لون.
## خارج النطاق
لا محركات سريرية جديدة غير معتمدة، لا أشعة جاهزة، لا إنشاء نسخ مستقلة من finance/inventory لكل تخصص.
## الإغلاق
تجربة لكل تخصص ومركز متعدد، ثم role matrix وصلاحيات وتداخل فروع واستئناف وانقطاع وتزامن. صور وخرائط modules وsetup موثقة، verify وCI. لا يُعلن اكتمال سيناريو يعتمد على موديول غائب.
## قواعد ملزمة عند التنفيذ
- هذا ملف تخطيط معتمد على تقرير المرحلة صفر الذي أرسله المالك، وليس فحصًا مستقلًا للكود. خط الأساس المبلّغ: main عند 74ad659؛ وثائق المرحلة صفر في PR #39، commit 621de78. تحقق من الحالة الحالية قبل العمل ولا تعد تنفيذ المكتمل.
- اقرأ تعليمات المشروع وdocs/delivery-plan/ أولًا. هذه الملفات تنظم التنفيذ ولا تمحو الأدلة التاريخية. سجل أي تعارض مع السبب والدليل.
- حافظ على الهوية المعتمدة: raclinic منتج Devware، العربية RTL وAlexandria، الإنجليزية LTR وInter، فاتح/داكن/حسب الجهاز.
- نفّذ مرحلة واحدة فقط. الأفكار الجديدة في قائمة انتظار؛ لا توسّع النطاق تلقائيًا. الأعمال المستقلة داخل المرحلة يمكن توزيعها بين الفريق.
- الأدوار المقترحة وظائف عمل وليست افتراضًا لوجود موظفين إضافيين. عيّن مسؤولًا ومراجعًا لكل مهمة عند بدء المرحلة.
- لا تغيّر صلاحيات سريرية أو سياسة مالية أو تسعيرًا كأثر جانبي لتحسين الواجهة. API هو مرجع التفويض؛ إخفاء الرابط لا يكفي.
- التطوير والتحقق في Codespace؛ لاحقًا النشر إلى staging عبر إصدارات محددة، وليس تعديل كود مباشر على الخادم.
- بيانات تجريبية فقط حتى اجتياز شروط التشغيل الحقيقي. لا أسرار في Git أو التقارير أو لقطات الشاشة.
- اعمل باستقلالية في القرارات الروتينية المصرح بها، مع احترام صلاحيات الأدوات وحماية الفروع. لا force push أو تجاوز CI.
- احفظ التقدم في سجل التنفيذ. الحالة: لم تبدأ / قيد التنفيذ / قيد المراجعة / مكتملة ومتحقق منها / متوقفة بسبب محدد.
- لا تدّع تحققًا لم تنفذه. افصل نتيجة اليوم عن الدليل التاريخي، والمحاكاة عن التكامل الحقيقي.
- الإغلاق: كود ومراجعة واختبارات مناسبة وفحص واجهة وتوثيق وأدلة على نفس commit. لا تبدأ المرحلة التالية تلقائيًا.
